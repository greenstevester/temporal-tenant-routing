Follow Tenant A’s work

User Alice -> Spring application -> Temporal namespace tenant-a
                                         |
                                 queue tenant-a-work
                                         ^
                                         | polled by
                                 Kubernetes tenant-a
                                 Spring Boot workers

User Bob   -> Spring application -> Temporal namespace tenant-b
                                         |
                                 queue tenant-b-work
                                         ^
                                         | polled by
                                 Kubernetes tenant-b
                                 Spring Boot workers

This is the local naming scheme. In Temporal Cloud, the full namespace includes your account identifier, for example tenant-a.acme123. Kubernetes still calls its namespace tenant-a. Both Temporal namespaces belong to the same shared Temporal service.

1. What each namespace separates

A tenant is one customer whose work must stay separate from another customer’s work. A Kubernetes cluster is a group of machines managed together. A node is one of those machines. A pod is Kubernetes’ running unit for containers. A Deployment maintains the requested number of pods and replaces them when needed. A Secret is a Kubernetes object for credentials or other confidential values. A Service gives pods a stable network address.

A Kubernetes namespace groups named resources. Both tenants can have a Deployment named temporal-worker because each Deployment is in a different namespace. Secrets, Services, and pods are also namespaced. Nodes and some administrative resources belong to the whole cluster. A namespace alone does not prevent network traffic, reserve a machine, or forbid users from reading another namespace. Add permissions, network rules, and resource limits. Kubernetes namespaces, multi-tenancy.

A workflow is your Java code for coordinating a job. A workflow execution is one running or completed instance of that code. Temporal records its progress as an event history. An activity is a piece of work called by a workflow, such as charging a card or calling another service. Workers are your application processes that run workflow and activity code. Workflow executions, activities.

Authentication checks a caller’s identity; authorization checks its permissions. A credential, such as a secret key, lets the caller prove its identity.

A Temporal namespace groups workflow executions, task queues, and namespace settings such as history retention. A workflow identifier belongs to that Temporal namespace. Authorization can restrict a credential to a namespace when the service is configured to enforce it. Temporal namespaces.

Kubernetes namespace                     Temporal namespace
pods, Secrets, Deployments               workflows, history, queues
        |                                         |
        +----- configuration connects these ------+
                   no automatic relationship

Naming both tenant-a makes configuration easier to inspect. Temporal does not discover that name from Kubernetes or check where a pod lives. Our manifests pass the Temporal namespace explicitly. Our security design separately restricts who can use it.

2. How work reaches a worker

A task is a request from Temporal for a worker to do something. A workflow task asks the worker to run workflow code until it decides what should happen next. An activity task asks it to run an activity. A task queue is the named place workers ask Temporal for those tasks. Polling means asking for work and waiting for a response. Queues are created on demand; this project has no queue-creation command. Workflow and activity queues are separate task kinds even when their names match. Tasks, task queues.

For Alice’s request:

Alice                   Spring application         Temporal             A worker
  | login + POST /jobs         |                      |                    |
  |-------------------------->|                      |                    |
  |                    authenticate Alice            |                    |
  |                    resolve tenant-a              |                    |
  |                    select A client               |                    |
  |                    namespace=tenant-a            |                    |
  |                    queue=tenant-a-work           |                    |
  |                            |--- start workflow -->|                    |
  |<---- accepted + job id -----|                      |<-- poll workflow --|
  |                                                   |--- workflow task ->|
  |                                                   |<-- schedule step --|
  |                                                   |<-- poll activity --|
  |                                                   |--- activity task ->|
  |                                                   |<-- activity result-|
  |                                                   |                    |
  |                          another workflow task advances the workflow   |

The application chooses the Temporal namespace through WorkflowClientOptions. It chooses the workflow queue through WorkflowOptions. The workflow chooses the activity queue through ActivityOptions. The worker’s client selects its namespace; newWorker(queue) selects the queue it polls. Both ends must agree. The service sends tasks over the worker’s existing polling connection; it does not connect to a Kubernetes Service for that worker. Java client, Java workers.

In this project, both task kinds use tenant-a-work for A and tenant-b-work for B. Activities explicitly copy the workflow’s queue. The workflow cannot choose another Temporal namespace through activity options. An activity could create another client in its own code, so its credential must also prevent unauthorized access.

The task routing address is the Temporal namespace, task-queue name, and task kind. A queue name by itself does not identify a tenant globally. Workflow identifiers are helpful for auditing, but their spelling does not enforce tenant isolation.

3. Three different meanings of affinity

Mechanism Meaning What it guarantees
Tenant-specific routing A’s tasks use A’s namespace and queues; A’s workers poll those queues. Correctly configured workers receive only their assigned routes. Server permissions must reject unauthorized polling.
Temporal sticky execution Temporal tries to send later workflow tasks to the same worker because it has workflow state cached in memory. A performance preference with fallback. It gives no lasting ownership of a workflow to a pod.
Kubernetes node affinity Rules that choose which nodes may run a pod. Required rules constrain scheduling; preferred rules express a preference. They do not choose Temporal tasks.
Kubernetes pod affinity or anti-affinity Rules to place pods near, or apart from, other pods. Placement constraints or preferences, not Temporal access permissions.

Sticky execution applies to workflow tasks. If the preferred worker disappears or the cached state is unavailable, another eligible worker can rebuild state from history. This is called replay. The sticky queue’s schedule-to-start timeout controls fallback; the documented default is five seconds. This does not redirect work to a different tenant’s normal queue. Sticky execution.

Normal A queue -> A pod 1 -> cached workflow state
                     X      pod crashes
Normal A queue -> A pod 2 -> replay history -> continue

Kubernetes affinity can place A on dedicated nodes or spread A’s replicas across nodes. Required scheduling rules are stronger than preferences, but the usual IgnoredDuringExecution rules do not continuously evict a running pod after labels change. Dedicated nodes also require protected labels and controls that stop other tenants scheduling there. The supplied single-node minikube example uses no affinity rules. Assigning pods to nodes.

Your requirement needs tenant routing, namespace-specific credentials, and protection of those credentials. Sticky execution helps performance. Affinity may help machine placement or availability once you have multiple nodes.

4. Compare the two designs

Shared Temporal namespace                Separate Temporal namespaces
+---------------------------+            +------------+ +------------+
| namespace shared          |            | tenant-a   | | tenant-b   |
| A queue       B queue     |            | A queue    | | B queue    |
+----^-------------^--------+            +-----^------+ +-----^------+
     |             |                          |              |
  A workers     B workers                  A workers      B workers
Concern One namespace, tenant queues Namespace per tenant
Routing Separate queue names route both task kinds. Separate namespace and queue settings route both task kinds.
Security Standard namespace-wide permissions cover both queues. Queue naming is a convention. Namespace permissions can deny B access to A, including queues and history.
Credentials Different keys improve rotation and auditing, but keys with the same namespace permission still have the same reach. Each worker key belongs only to its own namespace.
Operations Fewer namespace settings and connections to manage. Still maintain per-tenant worker deployments. More namespaces, accounts, connections, monitoring, retention settings, and onboarding work.
Worker scaling Increase A replicas independently; B has its own queue and workers. Also scale independently; namespace capacity can be managed separately.
Busy tenant Separate workers prevent A consuming B’s worker slots. Namespace-wide limits and shared server capacity can still affect B. Cloud provides per-namespace limits and capacity controls. Shared infrastructure, account dependencies, and the shared application still need capacity planning.
Visibility Workflows share a namespace; application filters alone are insufficient access restrictions. Credentials can separate access to each namespace’s history and visibility.

For two tenants with this security requirement, start with one Temporal namespace per tenant. This is a recommendation for your constraints. A shared queue with fairness can suit other applications, but it allows shared workers and does not meet your dedicated-worker requirement. Temporal multi-tenant patterns, Cloud security.

Temporal Cloud’s built-in Write permission permits both starting workflows and running workers throughout the assigned namespace. It is not a queue-specific permission. Current custom-role documentation describes narrower actions on resources such as namespaces and marks the feature pre-release; it does not make our queue names access restrictions. Roles and permissions, custom roles.

On a self-hosted service, separate namespaces need an authorization policy. The default authorizer allows requests. A custom policy is possible, but enforcing queue-specific access must cover all operations, including history reads and task completion, not only polling. The supplied project uses namespace separation. Self-hosted security.

The authenticated identity determines the route:

verified Alice login -> server authority tenant:tenant-a -> fixed A client and A queue
verified Bob login   -> server authority tenant:tenant-b -> fixed B client and B queue
request X-Tenant-Id  -> ignored

This example has two password-authenticated demonstration users. A production login system should verify its signed login token, its issuer, intended recipient, and tenant membership before constructing the same trusted authority. If a user belongs to several tenants, validate their selected tenant against that membership. Do not concatenate a request header into a queue name.

The Spring configuration uses ordinary beans and the Temporal Java library, so the choices are visible. The official Spring Boot integration also exists; this project does not combine automatic worker registration with these explicit beans. Spring Boot integration.

Illustrative extracts, matching the complete source:

// AppConfiguration: a client is fixed to one Temporal namespace.
WorkflowClient a = WorkflowClient.newInstance(aConnection,
    WorkflowClientOptions.newBuilder().setNamespace("tenant-a.acme123").build());

// JobService: the server's trusted tenant mapping chooses this queue.
WorkflowOptions options = WorkflowOptions.newBuilder()
    .setWorkflowId("tenant-a/job/example-1")
    .setTaskQueue("tenant-a-work")
    .build();

// JobWorkflowImpl: both task kinds stay on the same tenant route.
ActivityOptions activityOptions = ActivityOptions.newBuilder()
    .setTaskQueue(Workflow.getInfo().getTaskQueue())
    .setStartToCloseTimeout(Duration.ofSeconds(30))
    .setHeartbeatTimeout(Duration.ofSeconds(5))
    .setDisableEagerExecution(true)
    .build();

// WorkerConfiguration: this worker polls only this client's namespace and queue.
WorkerFactory factory = WorkerFactory.newInstance(a);
Worker worker = factory.newWorker("tenant-a-work");
worker.registerWorkflowImplementationTypes(JobWorkflowImpl.class);
worker.registerActivitiesImplementations(activities);
factory.start();

Cloud connections use setEnableHttps(true) and addApiKey(() -> key) on WorkflowServiceStubsOptions. The key identifies the caller; the namespace option selects the requested namespace. Both must be correct. Local mode refuses a nonempty key so it cannot send Cloud credentials over its unencrypted connection. Java connection configuration.

6. Crashes, replacement, and isolation

Replay means rerunning workflow code against its recorded events to reconstruct where it had reached. Completed activity results come from history. Replay does not call those completed activities again. Workflow code must be deterministic: the same recorded events must lead to the same commands. Use Temporal’s timers and workflow methods instead of ordinary sleeping, network calls, or random values in workflow code. Workflow definitions, event history.

Event Expected behavior
One A worker crashes during a workflow task A task is retried; another eligible A worker replays history and continues. Sticky state is expendable.
A worker crashes during an activity Temporal detects missed heartbeats or an attempt timeout and retries according to the activity policy.
An activity finishes its external effect but its completion is lost The activity may run again. Use a stable operation identifier so the external system can reject duplicate effects.
Every A worker stops A’s work waits. B’s correctly configured workers keep polling B. Timeouts and retry limits still apply.
Replacement A workers start They poll the same namespace and queue, register the same types, replay compatible workflow history, and continue. No pod-local workflow backup is required.

A heartbeat is an activity’s periodic report that it is still working. This example sends one each second during its simulated ten-second activity. It allows five seconds without a heartbeat, thirty seconds per attempt, at most twenty attempts, and ten minutes overall for each activity. A longer outage can therefore fail an activity. Recovery is governed by the configured limits, rather than a promise to retry forever. Activity failure detection.

Any compatible, authorized A worker can continue. Compatibility includes understanding the workflow’s recorded history and registering the required workflow/activity types. The example does not use worker versioning. Real deployments need a code compatibility strategy before changing long-running workflows.

The included activities only log and wait; there is no payment or database write. Disabling eager activity execution makes the ordinary activity-polling path visible. No local activities are used. Local activities would run in the workflow worker process and need separate consideration when designing worker placement.

A wrongly configured worker is stopped by our startup checks. A malicious worker can remove those checks. The enforceable restriction is its credential: Temporal must deny B’s credential in A’s namespace. Kubernetes must stop B reading A’s Secret or creating a pod that mounts it. A stolen A credential can be used outside A’s Kubernetes namespace unless additional controls prevent that. Temporal credentials alone do not prove physical pod location. Isolation controls.

Run the project commands inside your Linux terminal. The scripts use Bash, Linux paths, and Linux container images. Windows Subsystem for Linux 2 runs that Linux environment on Windows.

Use a Linux distribution such as Ubuntu with either Docker Engine installed inside it or Docker Desktop’s integration enabled for that distribution. Both are supported by minikube. Confirm docker info works as your regular Linux user before starting minikube. Official Windows/Linux setup.

Start the local demonstration

From the project directory:

./scripts/start-minikube.sh
./scripts/build-minikube.sh
./scripts/deploy-minikube.sh local
./scripts/test-minikube.sh local

The start script creates profile temporal-tenants with Kubernetes 1.37.2, the Docker driver, the containerd container runtime, and Calico networking. A container runtime starts containers. Calico is the networking component that enforces the supplied NetworkPolicy rules. Minikube’s default networking does not necessarily enforce those rules, so use this profile from the start. Minikube network policies.

The build script runs mvn verify, then minikube image build inside this profile. It gives the image a tag derived from the packaged Java file’s checksum. Deployments use imagePullPolicy: Never, so Kubernetes uses that exact local image. You do not need a registry, Docker login, or the minikube docker-env setup. Minikube image building.

The deployment creates application, tenant-a, tenant-b, and temporal-system namespaces. The last contains the Temporal development server. It has no authorization and keeps state only in memory. Killing workers preserves progress; killing that server loses the local test history. This is a worker-recovery exercise, not a durable service installation. Temporal development server.

The test normally takes several minutes. Its last local-mode line must say:

Routing and recovery passed. Local Temporal authorization is NOT enforced.

It also reports the directory containing its evidence. Seeing cross-tenant access accepted in local mode is an expected result. The Cloud exercise requires that access to be rejected.

Inspect a running demonstration

List the two worker deployments:

kubectl --context temporal-tenants -n tenant-a get pods
kubectl --context temporal-tenants -n tenant-b get pods
kubectl --context temporal-tenants -n tenant-a logs deployment/temporal-worker --tail=40

Open the local Temporal browser interface by leaving this command running:

kubectl --context temporal-tenants -n temporal-system port-forward \
  --address 127.0.0.1 service/temporal 8233:8233

Use http://localhost:8233 in your browser. If Windows localhost forwarding is disabled in your environment, inspect it from inside the Linux environment or enable that forwarding. Do not rely on the address from minikube ip being reachable from Windows. Windows/Linux minikube networking.

To call the application manually, first stop any test using port 18080, then leave this running:

kubectl --context temporal-tenants -n application port-forward \
  --address 127.0.0.1 service/tenant-application 18080:8080

In another Linux terminal, from the same project directory:

umask 077
mkdir -p .local/manual
printf 'user = "alice:%s"\n' "$(cat .local/alice-password)" > .local/manual/alice.curl
curl -fsS --config .local/manual/alice.curl --cookie-jar .local/manual/cookies \
  http://127.0.0.1:18080/csrf > .local/manual/token.json
token=$(jq -r .token .local/manual/token.json)
header=$(jq -r .headerName .local/manual/token.json)
curl -fsS --config .local/manual/alice.curl --cookie .local/manual/cookies \
  -H "$header: $token" -H 'Content-Type: application/json' \
  --data '{"jobId":"manual-1"}' http://127.0.0.1:18080/jobs
curl -fsS --config .local/manual/alice.curl http://127.0.0.1:18080/jobs/manual-1/result

The first response accepts the job. The result endpoint returns a waiting response until the job completes, usually after about thirty seconds. The /csrf endpoint supplies a browser request-forgery token: send it with its session cookie when starting a job. Authentication is still required on every protected request. Use a new job identifier for each new job.

Passwords are generated during deployment. Alice belongs to A and Bob to B. For Bob, use .local/bob-password and username bob. Do not expose this password-based demo application to a public network. Production needs an encrypted front connection and your real login system.

Test access restrictions with Temporal Cloud

The workers and application run inside minikube. Temporal runs in your Cloud account. This exercise needs two disposable Temporal namespaces and four separate machine identities. A machine identity is an account used by a program, called a Service Account in Temporal Cloud.

Use full namespace names such as tenant-a.acme123 and tenant-b.acme123. Replace acme123 with your real account identifier. Namespace names and endpoints come from your account; this project does not create paid Cloud resources or invent credentials.

Give each process only its required access

Create namespace-scoped Service Accounts with these permissions:

Identity Namespace permission Used in
tenant-a-worker Write on A only A’s worker Secret
tenant-b-worker Write on B only B’s worker Secret
tenant-a-application Write on A only Application Secret
tenant-b-application Write on B only Application Secret

Namespace-scoped accounts have the Read account role and one namespace permission. Account metadata access and workflow-history access are different permissions. Avoid Global Admin, Account Owner, and extra grants. Use separate accounts for separate trust boundaries; two keys on one broadly authorized account do not restrict each other. Service Accounts.

The built-in Write permission includes worker polling and task completion as well as workflow operations. It does not offer a worker-only restriction within that namespace. Granting it only on A gives this example the required cross-tenant boundary. Namespace permissions.

Create a key for each account and verify that A’s accounts have no access to B and vice versa. Do not paste keys into source files. New or changed keys may take time to become usable at the namespace endpoint; check access before interpreting a denied request as evidence of isolation. Cloud keys.

The final test message must say:

The probe runs in Kubernetes tenant-b, mounts B’s worker Secret, and first accesses B. It then requests A’s workflow tasks, A’s activity tasks, and A’s history. After testing, unset credentials from your shell and revoke the disposable keys when no longer needed. Key values also remain in .local/ and Kubernetes Secrets until you remove them.

unset TENANT_A_KEY TENANT_B_KEY TENANT_A_WORKER_KEY TENANT_B_WORKER_KEY

What keeps the tenants separate

verified login -> fixed tenant route -> Temporal namespace permission
                                               ^
                                               |
pod placement -> tenant's private Secret -> tenant's credential

Routing decides where work is offered. Authorization decides whether a caller may request it. Authentication proves which caller is asking. All three are needed for this design.

Controls in the example

Control Purpose Limit
Server-side tenant mapping Ignore a forged tenant header and select a configured route. A compromised application has both application credentials.
Route and pod-namespace checks Stop accidental deployment with A settings in B. Malicious code can remove checks or lie about its identity.
Namespace-scoped Cloud credentials Reject B’s calls to A’s namespace. A stolen A credential can be used wherever the endpoint is reachable.
Secret in each Kubernetes namespace Mount only that tenant’s worker key. Anyone allowed to create pods in A may be able to mount A’s Secrets.
No worker permission bindings; no mounted Kubernetes token Workers have no granted Kubernetes management powers. Cluster administrators and host administrators remain trusted.
Restricted pod policy Reject privileged workloads and enforce selected container restrictions. A shared kernel and shared cluster still have security risks.
NetworkPolicy Restrict traffic paths to required connections. It cannot distinguish two Temporal namespaces served by the same endpoint.
ResourceQuota and container limits Bound each tenant’s requested resources and container usage. Single-node contention and shared Temporal/application capacity remain.

Kubernetes permissions are called role-based access control. They decide which identities may read or change resources. This project grants its worker Service Accounts no extra roles and sets automountServiceAccountToken: false. That disables the usual automatic Kubernetes credential mount; it does not affect the separately mounted Temporal credential. Permission practices.

Do not give Tenant B permission to get, list, or watch A’s Secrets. Also deny creation or modification of A’s pods, Deployments, and other workload controllers, entry into A’s running containers, and changes to permission bindings. Pod creation can grant indirect access to a Secret even when direct Secret reads are forbidden. Namespace labels used by network policies must be protected too. Workload creation risks.

The deployments run as a non-root user, use a read-only container filesystem, drop extra Linux capabilities, and disable privilege escalation. The application and workers have a writable temporary directory. Kubernetes Secrets require proper administrative protection and, for a real installation, encryption at rest and a reviewed secret-delivery process. Encoding a Secret value is not encryption. Kubernetes Secret practices, pod security standards.

Network policies only work with a network component that enforces them. The scripts choose Calico. Policies are additive: another broad allow policy can weaken your intended restrictions. The application has no public ingress; the exercise reaches it through authenticated local port forwarding. Public Cloud traffic is restricted to port 7233, but its destination rule covers public addresses rather than a particular domain name. NetworkPolicy behavior.

A compromised worker

If B’s worker is compromised, assume its B credential is stolen. Proper namespace permissions still deny requests to A. B’s own work can be damaged, and a worker might falsely report its own execution location. Worker identity strings and returned location records are audit clues; they are not cryptographic proof of physical placement.

For A’s work to run only inside Kubernetes tenant-a, control who can obtain A credentials, who can deploy A workloads, which images run there, and which machines can reach Temporal. Protect deployment administration as well as worker runtime identities. If hostile tenants control their own hosts or require stronger machine isolation, consider separate clusters or other stronger execution boundaries. Namespace names cannot supply that guarantee. Kubernetes tenant isolation, Cloud access controls.

Rotate each tenant’s keys independently and verify revocation at the service. Do not put administrator credentials, the other tenant’s keys, or the application’s two keys into worker pods. The shared application is trusted across both tenants, so protect and audit it accordingly.

What the supplied check can establish

The test checks representative Kubernetes permissions using administrator impersonation of B’s Service Account. It also sends real Temporal requests from a pod holding only B’s key. It catches incorrect namespace grants and obvious credential mixups. It does not test every possible Kubernetes permission, container escape, stolen administrator credential, or host attack. The local unauthenticated Temporal server intentionally accepts cross-tenant calls.

The two-tenant minikube test

Run ./scripts/test-minikube.sh local after local deployment, or cloud after secured deployment. The test uses the already built image and refuses a mismatch with the application’s deployed image. It always targets context temporal-tenants.

  1. Start a job for Alice and a job for Bob. Send a forged A tenant header with both requests; Bob must still use B. Save the initial pod lists.
  2. Wait for the log proving an A activity is processing, then force-delete that busy pod. Wait for both jobs to finish. A’s processing attempt number must be greater than one.
  3. Scale A’s worker Deployment to zero and wait until its worker pods disappear.
  4. Start another job for each tenant. B must finish while A has no workers. A’s status must remain running; its job is waiting for work to be performed.
  5. Restore A to two replicas. The original waiting job must finish on replacement A pods.
  6. Check every returned activity’s tenant, Temporal namespace, queue, Kubernetes namespace, and pod name. Check workflow-task worker identities from Temporal history against recorded Kubernetes pod names too.
  7. Check that B’s Kubernetes identity cannot read or list A’s Secrets, create A pods or Deployments, or enter A pods.
  8. Launch the access probe in B with B’s worker key. In Cloud mode, require explicit denial of A workflow polling, A activity polling, and A history access. First prove access to B works.

Interpreting the result

Result Meaning
Routing and recovery checks pass The tested workers and configuration kept both task kinds on the intended tenant route through these failures.
SECURITY_DENIAL_PASSED B could access B, while its A polling and history calls received explicit access rejection.
LOCAL_SERVER_ACCEPTED_CROSS_TENANT_ACCESS The local service accepted B’s request for A history. Local Temporal authorization is absent.
A permission probe times out Inconclusive access control; the test fails. An empty queue can make an authorized poll wait.
A probe reports missing history The setup or identifier is wrong; the test fails. Missing data is not access denial.

The test can disprove isolation for the exercised routes if it observes cross-tenant execution or unauthorized access. Passing this finite exercise does not prove resistance to all possible attacks. Pod metadata and worker identity are checked together, but malicious worker reports still require independent operational controls.

Worker outage and service outage are separate tests. This project tests worker outages. The local development server is ephemeral, and no test kills it. Durable service failover, storage recovery, long outages beyond activity time limits, workflow-code version changes, and large tenant counts need separate tests in a suitable environment.

Using a self-hosted Temporal service

A self-hosted service is Temporal operated by your own team. The same namespace-and-queue routing works, but you are responsible for service authentication, authorization, encryption, availability, and capacity.

The development server included here is intentionally unauthenticated. Its two namespaces organize work without restricting who may access it. Adding a namespace or inventing a different queue name does not change that.

Temporal’s self-hosted security configuration separates two jobs:

  • A ClaimMapper reads a validated identity and its permissions from the request’s credentials.
  • An Authorizer decides whether those permissions allow the requested operation.

The default no-op authorizer permits calls. Configure actual verification and authorization before treating namespaces as security boundaries. The standard authorization model includes namespace roles such as reader, writer, worker, and administrator. A namespace-scoped worker role can distinguish worker operations from starting workflows more narrowly than the Cloud Write role used in this example. Temporal self-hosted security.

caller credential -> verified identity -> namespace permissions -> operation allowed or denied

Encrypted connections protect data in transit. Client-certificate authentication can identify a caller, but its certificate still needs an authorization policy. Network rules that allow both tenants to reach the same Temporal address cannot inspect the namespace requested inside that encrypted connection.

Separate self-hosted namespaces still share whatever server processes, storage capacity, and networking you assign them. Apply appropriate per-namespace request limits and measure the shared service under load. Kubernetes worker quotas alone do not constrain service-side usage. Temporal service configuration.

This archive does not include a production self-hosted service, an identity issuer, or a custom authorizer. Its secured connection code uses Cloud keys and public server certificates. For a self-hosted installation, adapt Connections.java to the credentials and trusted certificates provided by your platform team, then repeat the same positive B-access and negative A-access tests. The exact credential format must come from that service’s configuration.

If you keep tenants in one Temporal namespace, a custom queue-aware authorization design must also address operations without a queue name, such as reading workflow history and completing tasks using task tokens. A queue-prefix check on polling alone does not establish tenant data isolation. Separate namespaces avoid that additional policy design in this starting example.

What I cheated on

  • scripts/start-minikube.sh, scripts/build-minikube.sh, scripts/deploy-minikube.sh, and scripts/test-minikube.sh were not executed against a cluster here. This machine runs macOS, and no minikube installation or Windows/Linux environment was available. Shell checks and offline rendering do not prove cluster behavior.
  • Dockerfile was not built into a container image here. Its base image manifest was checked, and the Java package compiled successfully. Container startup and the chosen memory limits still need the supplied minikube exercise.
  • AccessProbe.java was not run against real Cloud credentials. The Java tests check its treatment of accepted calls, permission rejections, and timeouts. The full live sequence is exercised by scripts/test-minikube.sh cloud.
  • DemoActivities.java simulates work with logging and a timed wait. It has no external business effect and therefore does not demonstrate duplicate protection for payments or database writes.
  • SecurityConfiguration.java has two demonstration users with generated deployment passwords. A production identity provider is not included. Namespace names ending in acme123 in the documentation are placeholders for your Cloud account.
  • WorkflowTest and JobServiceTest use recording activities; WebSecurityTest mocks Temporal job operations. Framework startup, main methods, and every possible failure branch are not individually tested.
  • k8s/local-temporal.yaml has no Temporal authorization and keeps service state in memory. Service durability, production self-hosted configuration, and storage recovery are outside this demonstration. No deployments or infrastructure changes were made for this delivery.
